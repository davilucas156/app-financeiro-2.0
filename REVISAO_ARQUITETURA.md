## `src/features/painel/renda-do-mes/declararRenda.action.ts`

### Acoplamento e separação de conceitos
As 3 validações de borda (formato do mês, inteiro não-negativo, teto de R$ 10 milhões) são aceitáveis na action — nenhuma decide *o que* o sistema faz com a renda, só se a entrada é bem-formada; o teto é defesa contra erro de digitação, não regra de negócio, e é duplicado de verdade pelo banco (ver Thin Client/Fat Server abaixo). **Média**: `revalidatePath("/painel")` é path morto confirmado — grep em `src/app/` não encontra nenhuma rota `/painel`; um comentário em `categorias/page.tsx` confirma que `/painel` foi uma rota de spec anterior já descontinuada. Não causa bug visível (`revalidatePath` com path inexistente é inócuo, e a linha seguinte já revalida `/dashboard`, a rota real), mas é resíduo de migração que confunde leitura futura. Recomendação: remover a linha.

### Tipagem e segurança de tipos
Sem `any`. **Baixa/Média**: `entrada: { mes: string; centavos: number }` é tipo inline não exportado, inconsistente com o padrão já estabelecido em `decidirLancamento.action.ts` (que exporta `EntradaDaDecisao`, importado e reusado pelo componente client `AcaoDeDecidir.tsx`). Um componente client que chamar `informarRenda` tem que repetir a forma manualmente. Recomenda-se extrair `export type EntradaDaRenda = { mes: string; centavos: number }`. A validação numérica (`!Number.isInteger(entrada.centavos) || entrada.centavos < 0`) está correta e cobre `NaN`/`Infinity`/fracionário sem lacuna.

### Thin Client / Fat Server
Sem achados. `usuario.id` vem exclusivamente de `garantirUsuario()`; `entrada` (cliente) só contém `mes`/`centavos`. Confirmado em `rendaDoMes.service.ts`: o upsert usa chave primária composta `(userId, mesReferencia)`, e a leitura também filtra por `userId` — nenhum vetor para afetar dado de outro usuário. Confirmado que a constraint `monthly_income_mes_ck` é real (não só comentário): existe em `src/db/schema.ts` e materializada na migration `0010_lonely_human_torch.sql`. Dupla validação de formato (regex na action + check constraint no banco) genuína.

### Duplicação e reuso
**Média**: o regex `/^\d{4}-\d{2}$/` (formato de mês) está duplicado em 3 lugares — `declararRenda.action.ts`, `importarExtrato.service.ts` e `removerOMes.service.ts` (este ao menos extraiu para uma constante local, mas não compartilhada) — sem um validador comum. Nenhum dos três valida o intervalo real 01–12 do mês (um "mês 13" passaria a regex nos três). Recomendação: extrair para algo como `src/lib/mesCompetencia.ts`. Positivo: o esqueleto estrutural de action (`garantirUsuario` → validar → service → try/catch com log + `revalidatePath`) é consistente com `decidirLancamento.action.ts` — padrão idiomático bem reutilizado, não duplicação indevida.

## `src/features/upload/desfazer-envio/desfazerEnvio.service.ts`

### Acoplamento e separação de conceitos
Sem achados. Arquivo puramente server-only, sem UI/rota. As 3 operações (select de conferência, delete de `transactions`, delete de `imports`) são internas ao comportamento "desfazer um envio". Comparado com `removerOMes.service.ts`: o próprio `architecture.md` (linhas 449-458) já documenta e justifica por que os dois caminhos de deleção de `imports` não são centralizados — modelos de confiança de entrada diferentes (um envio = alça global do cliente, exige conferência de dono; um mês = não é alça de nada, não exige). Não é duplicação acidental.

### Tipagem e segurança de tipos
Sem `any`. União discriminada bem definida. Regex de UUID como defesa de tipo-em-runtime é bom padrão (evita query inútil com id malformado). **Baixa**: ausência de `try/catch` interno é aceitável — delega tratamento de erro de infraestrutura para a action, e o rollback automático da transação Drizzle já cobre atomicidade entre os dois deletes. **Média**: não existe `desfazerEnvio.test.ts` — o comportamento de segurança "envio de outro dono retorna a mesma mensagem que envio inexistente" depende hoje só de leitura de código, sem teste automatizado travando contra regressão futura.

### Thin Client / Fat Server
**Sem achados — checagem de segurança mais importante da rodada, verificada linha a linha.** Confirmado que `userId` passado a `desfazerImportacao` vem exclusivamente de `garantirUsuario()` na action irmã, nunca do `FormData`. As três queries dentro da transação (select de conferência, delete de `transactions`, delete de `imports`) **todas** incluem `eq(X.userId, userId)` — a autorização é reafirmada em cada statement, não só no select inicial. TOCTOU entre o select e os deletes não é explorável: mesmo numa hipótese de mudança de dono entre as duas operações (não suportada pelo schema), os deletes têm seu próprio filtro idêntico — o pior caso é apagar 0 linhas, nunca dado de outro usuário.

### Duplicação e reuso
Sem achados para o regex de UUID (único no projeto, nenhuma duplicação). **Baixa**: a estrutura "apagar transactions + import" é parecida com `removerOMes.service.ts`, mas a semelhança é superficial — `desfazerEnvio` já conhece o `importId` e confirma dono antes; `removerOMes` descobre o id via `returning` do delete de `transactions` para fechar uma janela de corrida específica daquele fluxo, e trata "zero resultado" como sucesso (não erro). Unificar os dois exigiria abstrair uma diferença de contrato real — candidato a refactor futuro sem urgência, não um bug.

## `src/features/classificacao/revisar-lancamento/decidirLancamento.action.ts`

### Acoplamento e separação de conceitos
**Média** (achado principal da rodada): a função `montar()` cruza a linha entre "traduzir formato" e "decidir regra de negócio" em dois pontos. (1) Resolve `fonte: "sugestao" | "manual"` a partir de uma lista estática `FONTES` replicada na action — é uma classificação com significado de negócio, não desembrulhar transporte (diferente de `importarExtrato.action.ts`, rodada 24, que não decidia nada). (2) A regra composta `comValor: e.sempre === true && e.comValor === true` duplica uma invariante que o próprio `decidirLancamento.service.ts` já documenta em comentário ("sem `sempre` não há regra para estreitar") — a action replica a regra antes do service aplicá-la, criando risco de divergência silenciosa se a regra mudar só num dos dois lugares. Recomendação: mover a resolução de `fonte` e a regra `sempre`/`comValor` para o service ou para `motor/sugestoes.ts`.

### Tipagem e segurança de tipos
Sem `any`. `EntradaDaDecisao.tipo: Decisao["tipo"]` reusa corretamente o tipo do service. `fonteDaSugestao?: string` validado contra união fechada via `FONTES.find(...)` é o padrão correto de type guard informal. **Baixa/informativa**: `categoriaId`/`lancamentoId` não têm validação de formato (UUID) nesta action, diferente de `desfazerEnvio.service.ts` (mesma rodada), que valida antes de consultar. Verificado por grep em `decidirLancamento.service.ts`: os ids vão direto para `eq(...)` sem checagem de formato prévia — mas isso não é falha de segurança (um id malformado contra coluna `uuid` do Postgres gera erro de tipo, não acesso indevido), só uma inconsistência de robustez entre os dois arquivos — `desfazerEnvio` falha com mensagem amigável antes de tocar o banco; aqui o Postgres rejeitaria com erro de tipo bruto.

### Thin Client / Fat Server
Sem achados. `usuario.id` vem exclusivamente de `garantirUsuario()`. Confirmado em `decidirLancamento.service.ts`: tanto `categoriaId` quanto `lancamentoId` do cliente são sempre conferidos com `eq(..., userId)` antes de qualquer leitura/gravação — mesma mensagem genérica para "não existe" e "não é seu", evitando enumeração. A action delegar essa conferência ao service (em vez de duplicá-la) é o desenho correto, documentado explicitamente no próprio service. `fonteDaSugestao` do cliente é puramente informativo (metadado de procedência) — não participa de decisão de autorização nem de criação de regra; um cliente mentindo sobre a fonte não ganha privilégio.

### Duplicação e reuso
**Média**: `FONTES` em `decidirLancamento.action.ts` é cópia manual dos 4 literais de `FonteDeSugestao` (`motor/sugestoes.ts`), que é uma union de string literals pura — não um array `as const` com tipo derivado. O TypeScript não avisaria se a union ganhasse um 5º valor: `FONTES` continuaria com 4 itens, e esse novo valor nunca resolveria para `fonte: "sugestao"`, caindo silenciosamente em `"manual"` sem erro de compilação. Recomendação: inverter a relação — definir `FONTES_DE_SUGESTAO` como array `as const` em `motor/sugestoes.ts` e derivar `FonteDeSugestao` dele; a action importaria o array em vez de replicá-lo.

## Resumo e prioridade de ação

1. **Regra de negócio na camada errada, com risco de divergência silenciosa**: `decidirLancamento.action.ts` decide a "fonte" da sugestão e replica a regra composta `sempre`/`comValor` que o `.service.ts` já trata como invariante documentada — se a regra mudar num lugar só, a divergência não teria teste cruzado para pegar. Mover ambas para o service ou para `motor/sugestoes.ts`.
2. **Duplicação frágil sem checagem do compilador**: `FONTES` (decidirLancamento.action.ts) é cópia manual de `FonteDeSugestao` (union de literais); um 5º valor futuro na union quebraria silenciosamente a classificação "sugestão vs. manual" sem erro de build. Inverter para array `as const` → tipo derivado.
3. **Falta de teste de regressão para comportamento de segurança**: `desfazerEnvio.service.ts` não tem `.test.ts` cobrindo "envio de outro dono retorna a mesma mensagem que envio inexistente" — hoje correto por leitura de código, mas sem trava automatizada.
4. **Dead code de rota descontinuada**: `declararRenda.action.ts` chama `revalidatePath("/painel")`, rota que não existe mais (resíduo de spec anterior) — remover a linha.
5. **Duplicação de validação de formato de mês sem validar intervalo real**: regex `/^\d{4}-\d{2}$/` repetido em 3 arquivos, nenhum valida 01–12; candidato a extrair para `src/lib/`.
6. **Resultado positivo, maior superfície de risco da rodada confirmada segura**: `desfazerEnvio.service.ts` — a operação destrutiva guiada por id do cliente reafirma `userId` em todas as 3 queries, sem janela de TOCTOU explorável; `declararRenda.action.ts` tem dupla validação real (regex + check constraint) confirmada no schema e na migration, não só em comentário.
